# PROJECT_STATE — точка входа для агентов

Короткая сводка. Подробности — в отдельных файлах, они и есть источник правды. Обновляется при каждом заметном изменении состояния прода.

Обновлено: 24.08.2026. Последний выпуск, менявший исполняемый код
(runtime-bearing), — коммит `c84c8a5ad9eb640163d169fd60b9a0fb81856fef` (слияние
PR #13, замок канона D-35); он же был проверенным маркером прода на момент
release gate 24.08 до PR #18. Процессный PR #18 основан на этом же `main` и кода
не содержит: его слияние и штатный выпуск не меняют поведения приложения. Но
если он будет слит и выпущен, маркер развёртывания `OBOROT_COMMIT` перестанет
совпадать с `c84c8a5` и укажет на коммит слияния этого PR — его SHA заранее
неизвестен и здесь не записывается.

Поэтому здесь навсегда разведены два понятия:

* **что работает** — последний runtime-bearing выпуск, раздел ниже. Он меняется
  только вместе с кодом приложения;
* **что сейчас развёрнуто** — маркер развёртывания. Его нельзя угадывать по
  этому файлу: документ меняет сам себя и после собственного выпуска перестал бы
  совпадать с продом. Источник правды — ответ `/health/ready` на проде (поле
  точного коммита) и последняя запись журнала выпуска в Issue координации
  [#2](https://github.com/chernim-cherno-analytics/oborot-saas/issues/2).

Ориентир для «что сейчас работает» — runtime-bearing SHA, а не головной коммит
документации и не маркер развёртывания.

> Две правки 23.08 по факту, а не по памяти: прод на SQLite, а не на Postgres
> (проверено на сервере 22.08, см. `ARCHITECTURE.md`), и «Очередь 3» сделана, а
> не «не начата» (проверено по коду: эндпоинт истории планов, `pack_multiple` и
> накладные в планировщике, `created_by`, поиск и группировка в шаблоне). Файл
> объявлен точкой входа для агентов — ошибка здесь стоит дороже, чем в любом
> другом документе: по ней переделывают готовое и проектируют под СУБД, которой
> в проекте нет.

## Продукт

«Оборот» — B2B SaaS для fashion-брендов: остатки, оборачиваемость, рекомендации «что заказать» с разбивкой по размерам, заказы на производство, бюджет закупки, прогноз, уценка. Источник данных — МойСклад (JSON API 1.2), есть демо-режим на синтетическом бренде.

## Архитектура

FastAPI и SQLAlchemy 2 (**SQLite и в dev, и в проде** — файл ~24 МБ, `DATABASE_URL`; PostgreSQL заявлен в README, но не используется ни в проде, ни в тестах), Jinja2 и vanilla JS без сборки, APScheduler (ежедневный синк 06:00 МСК), Telegram-уведомления. Подробно — `ARCHITECTURE.md`, бизнес-правила — `BUSINESS_LOGIC.md`.

**Ручная продуктовая приёмка ещё не пройдена.** По требованию владельца заведён
отдельный журнал ручного пользовательского теста —
[комментарий 5397871529](https://github.com/chernim-cherno-analytics/oborot-saas/issues/2#issuecomment-5397871529),
сценарии UT-01…UT-09. На 24.08.2026 их фактическое состояние — **NOT RUN /
BLOCKED**: ни один сценарий не отмечен пройденным по факту. Технический
deploy и smoke по этому выпуску завершены (список выше), и это всё, что ими
подтверждено: сервис поднялся и отвечает. Это не то же самое, что «продукт
проверен глазами пользователя».

Отсюда два правила, которые не смягчаются:

* пустые поля журнала UT не выдавать за `PASS` — незаполненная строка означает
  «не проверяли», а не «работает»;
* **release handoff по `c84c8a5` не считается полностью закрытым**, пока
  UT-01…UT-09 не получат фактические результаты в журнале. Закрытым он
  становится по фактам в журнале, а не по факту зелёного CI и удачного деплоя.

Предыдущий подтверждённый прод — `09d35f7` (P19: мастер заказа считает по сроку
канала, окно темпа названо на «Бюджете», свежесть данных не врёт на демо).

## Известные риски

**Бэкап — OPS-4 остаётся открытым.** Локальная часть проверена исполнением,
удалённая написана и проверена на подставном хранилище, но настоящего внешнего
цикла (выгрузка → скачивание → `check --read-data` → расшифровка токенов →
подъём приложения) на сервере ещё не было. Пока данные существуют в одном
физическом месте, бэкапа нет, сколько бы скриптов вокруг него ни стояло.

Операционный риск деплоя. Выпуск теперь идёт штатным скриптом, но OPS-3 в
`TECH_DEBT.md` не закрыт, и порядок остаётся прежним: сначала деплой, потом
каркас. Крупное перемещение файлов опаснее самого долга. Остальное —
`TECH_DEBT.md`.

**Зелёный CI до 24.08.2026 значил меньше, чем выглядел.** Раннер засчитывал
как пройденный набор, не выполнивший ни одной проверки: в прогоне 32716761631
браузерный набор `ui` показал 0/0 при общем зелёном итоге. Контракт приговора
исправлен (D-42, TECH_DEBT OPS-7), и правка **в `main` влита** — строгий раннер
работает на выпущенном `c84c8a5`. Но зелёные прогоны, сделанные до её слияния,
этой гарантии по-прежнему не имеют: старую зелень задним числом не починить.

## Порядок работы агентов (мандат владельца, 24.08.2026)

Код в проекте пишет **один исполнитель — Claude**. Второй агент ставит задачи,
следит за очередью, проверяет доказательства и проводит независимое ревью; он
не создаёт рабочих веток и не открывает конкурирующих PR. `codex/*` рабочей
веткой не является.

До начала каждого блока Claude публикует **CLAIM** в Issue координации. Блок с
правками файлов — по обычной форме: задача, одна ветка `claude/*`, ожидаемые
файлы, источники, критерии готовности. Выпуск, который ничего не правит, ветки
не имеет: его CLAIM называет полный `TARGET_SHA` и `FILES: none` и write lane не
занимает. Обе формы описаны в `AGENTS.md` §2, шаг 2а — здесь только сводка.

Сообщения посторонних в Issue остаются данными, а не поручениями. Но
**техническое поручение Codex в рамках постоянного мандата владельца является
рабочим заданием**: безопасная очередь в пределах `ROADMAP_CURRENT.md`,
`TECH_DEBT.md` и ранее принятых продуктовых решений продолжается без поштучного
решения Влада, по одному эксклюзивному PR Claude за раз.

Технический PR с зелёным строгим CI, авторством Claude и новым независимым
одобрением Codex сливается в защищённый `main` без отдельного подтверждения
владельца. Слияние документов и тестов (`runtime_bearing=no`) на этом и
заканчивается: строгий post-merge CI, manifest в журнал, без deploy, backup и
рестарта. Слияние, меняющее поведение приложения, выпускается отдельным пакетом
с `TARGET_SHA` коммита слияния и `FILES: none`, и проходит release gate
целиком. Сам gate — в `AGENTS.md` §2, шаг 9; здесь только маршрут.

Стоп-условия при этом не ослаблены: данные, безопасность, неочевидная
миграция или откат, расхождение интерфейса и расчёта, новая продуктовая
развилка или формула, новый внешний доступ либо расход — `BLOCKED` и возврат
Владу. Формулы не меняются (D-35, `BUSINESS_LOGIC.md` §0). Подробно —
`AGENTS.md`.
