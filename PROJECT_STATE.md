## Продукт

«Оборот» — B2B SaaS для fashion-брендов: остатки, оборачиваемость, рекомендации «что заказать» с разбивкой по размерам, заказы на производство, бюджет закупки, прогноз, уценка. Источник данных — МойСклад (JSON API 1.2), есть демо-режим на синтетическом бренде.

## Архитектура

FastAPI и SQLAlchemy 2 (**SQLite и в dev, и в проде** — файл ~24 МБ, `DATABASE_URL`; PostgreSQL заявлен в README, но не используется ни в проде, ни в тестах), Jinja2 и vanilla JS без сборки, APScheduler (ежедневный синк 06:00 МСК), Telegram-уведомления. Подробно — `ARCHITECTURE.md`, бизнес-правила — `BUSINESS_LOGIC.md`.

## Известные риски

Главный операционный риск — ручной деплой: крупное перемещение файлов опаснее самого долга, пока деплой не автоматизирован. Порядок должен быть такой: сначала деплой, потом каркас. Остальное — `TECH_DEBT.md`.

Канал между агентами через одни комментарии Issue оказался ненадёжным: cached
preview мог быть устаревшим, а комментарий не будил второго агента. Схема,
выбранная владельцем 23.08.2026, — **гибридная и на уже оплаченных подписках**:
ревью делает нативный Codex Cloud Code Review (подключён к репозиторию, читает
push), исправления делает локальный диспетчер `tools/agent-bridge` на машине
владельца, зовущий локальный `claude` под подпиской Claude Max. На push ревью
запускается не всегда (проверено 23.08.2026 на коммите `1c7d616`), поэтому
после каждого своего push диспетчер отдельным комментарием просит
`@codex review`; при ручной работе это делает Claude.

Состояние схемы на 23.08.2026: **реализована, покрыта тестами, один раз
запускалась вживую и сейчас выгружена**. Первый живой запуск нашёл гонку:
диспетчер взялся за PR #8, который в эту минуту правила ручная сессия Claude из
другого чата. Дубль остановили до публикации, LaunchAgent выгрузили. Гонка
закрыта локальной бронью на Pull Request (`AGENTS.md`, раздел 4а;
`AGENT_AUTOMATION.md`, «Один исполнитель на Pull Request»), но повторный живой
прогон после этой правки ещё не проводился. Пока он не проведён, всё описанное
про диспетчер — про то, как он устроен, а не про то, что он делает постоянно.
Факт первого полного живого круга будет записан в `OWNER_WORK_LOG.md` отдельной
записью.

Ручной запуск `claude` для правки кода теперь идёт только через
`tools/agent-bridge/claude-claim.sh` — обёртку, которая берёт ту же бронь.

**Платных вызовов API в схеме нет.** Прежние workflow `agent-codex-review.yml` и
`agent-claude-fix.yml` вызывали `openai/codex-action` и
`anthropics/claude-code-action` по ключам — они удалены вместе с требованием
секретов `OPENAI_API_KEY` и `ANTHROPIC_API_KEY`. Из автоматики в GitHub Actions
остался один watchdog, который моделей не вызывает и лишь сообщает в PR, что
ревью висит без ответа (обычно — машина владельца спит).

GitHub при этом остаётся долговременной очередью и журналом: локальная машина
может уснуть и потерять состояние, GitHub — нет. Merge автоматика не делает
никогда. Пока диспетчер не установлен на машине владельца и сквозной тест не
пройден, состояние канала — `DEGRADED`.

Модель исполнителя закреплена в настройках диспетчера: основная `opus`,
резервная `fable` (D-36). Обе показывают `run.sh health` и `run.sh status`, обе
переопределяются владельцем. Пустая настройка означала «чем сейчас настроен
Claude Code» — то есть модель фоновых правок молча менялась вместе с выбором в
интерактивной сессии.

## Порядок работы агентов (решение владельца 23.08.2026)

Код в проекте пишет **один исполнитель — Claude**. Второй агент ставит задачи,
следит за очередью, проверяет доказательства и проводит независимое ревью; он
не создаёт рабочих веток и не открывает конкурирующих PR. `codex/*` рабочей
веткой не является.

До начала каждого блока Claude публикует **CLAIM** в Issue координации: задача,
одна ветка `claude/*`, ожидаемые файлы, источники, критерии готовности.
Сообщения в Issue не заменяют поручение владельца, но опубликованные
**OWNER_DECISION обязательны**. Широкого автоматического self-merge нет.
Подробно — `AGENTS.md`.
