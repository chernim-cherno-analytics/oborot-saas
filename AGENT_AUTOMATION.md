# Автоматическая связь Codex → Claude

## Что здесь изменилось и почему

Первая версия этой автоматики жила целиком в GitHub Actions и вызывала платные
API: `openai/codex-action` с ключом `OPENAI_API_KEY` для ревью и
`anthropics/claude-code-action` с ключом `ANTHROPIC_API_KEY` для правок.

Решение владельца 23.08.2026: **гибридная схема на уже оплаченных подписках.**
Обе стороны цикла и так оплачены — ревью подпиской ChatGPT/Codex, правки
подпиской Claude Max. Платить за них второй раз через API незачем.

Поэтому:

* оба workflow с вызовом моделей удалены;
* секреты `OPENAI_API_KEY` и `ANTHROPIC_API_KEY` больше не нужны и не должны
  существовать в репозитории;
* ревью делает **нативный Codex Cloud Code Review**, уже подключённый к
  `chernim-cherno-analytics/oborot-saas` и настроенный проверять push (на деле
  срабатывает не всегда — см. «Почему круг замыкается просьбой»);
* исправления делает **локальный диспетчер** на машине владельца, который зовёт
  локальный авторизованный `claude`.

GitHub при этом остаётся ровно тем, чем и был: долговременной очередью и
журналом. Ревью, замечания, маркеры и отчёты живут в PR. Локальная машина может
уснуть, перезагрузиться и потерять всё своё состояние — GitHub не потеряет
ничего, и следующий цикл продолжит с того места, где остановились.

## Роли

| Кто | Где выполняется | Что делает | Чего не делает |
|---|---|---|---|
| Нативный Codex Cloud Code Review | облако OpenAI, по подписке | читает push и просьбу `@codex review`, оставляет ревью и inline-замечания к точному SHA | не меняет код, не пушит, не сливает, **не гарантирует ревью на каждый push** |
| Локальный диспетчер `tools/agent-bridge` | macOS владельца, LaunchAgent | опрашивает GitHub, собирает замечания, зовёт `claude`, гоняет тесты, коммитит, пушит и просит поревьюить новый SHA | не сливает PR, не делает merge/rebase/force-push, не вызывает API моделей |
| Локальный Claude Code | macOS владельца, подписка Claude Max | правит **только** названные замечания в файлах | не выполняет команд, не коммитит, не пушит, не трогает workflow и сам диспетчер |
| `agent-watchdog.yml` | GitHub Actions | замечает ревью **с замечаниями**, оставшееся без ответа, и пишет об этом в PR | **не вызывает ни одну модель**, не запускает исправлений, секретов не получает, на чистое ревью не реагирует |
| Владелец | — | принимает решение о merge | — |

Разделение «Claude правит файлы, диспетчер гоняет тесты и пушит» сделано
намеренно. Если бы `claude` сам делал commit и push, «зелёные тесты» и «то, что
уехало в ветку» перестали бы быть одним и тем же: между прогоном тестов и
пушем модель могла бы дописать ещё строку. Сейчас порядок жёсткий и проверяемый:
правка → тесты → commit → push, всё тремя разными процессами.

## Поток событий

1. Claude пушит новый SHA в ветку `claude/*`, PR открыт и не draft.
2. Нативный Codex Cloud Code Review просыпается на push сам и оставляет ревью:
   тело и inline-замечания, привязанные к точному commit SHA.
3. LaunchAgent будит диспетчер (примерно раз в минуту). Диспетчер берёт
   блокировку — параллельных прогонов не бывает.
4. Диспетчер находит открытые PR из веток `claude/*` **этого же репозитория**
   (форки отсекаются) и для каждого сравнивает `head.sha` с тем, к чему
   привязано ревью. Совпадение должно быть точным, по полному SHA. Привязка
   inline-замечания берётся из `pull_request_review_id` (через `commit_id`
   самого ревью) и `original_commit_id`, а **не** из его поля `commit_id`:
   см. ниже, «Куда переезжают замечания».
5. Ревью без замечаний («no issues found» и подобное) распознаётся и
   пропускается: будить модель ради пустого ревью — это шум в PR и трата
   подписки.
6. Есть замечания и они ещё не обработаны → диспетчер приводит **свою**
   рабочую копию ровно к этому SHA и зовёт `claude -p` с полным текстом ревью.
7. `claude` правит файлы. Инструменты ограничены чтением и правкой: команд он
   выполнять не может.
8. Диспетчер откатывает всё, что модель тронула в `.github/workflows/**` и
   `tools/agent-bridge/**`, и прогоняет тесты — той же командой, что CI:
   `python3 tests/run_all.py --jobs 3`.
9. Тесты зелёные → commit → `git push origin HEAD:refs/heads/<ветка>` без force.
10. Отчёт комментарием в PR: статус, старый SHA, номер попытки, изменённые
    файлы, результат тестов.
11. Ключевой исход дублируется в issue-канал координации (по умолчанию issue
    #2, настройка `OBOROT_BRIDGE_COORDINATION_ISSUE`). Комментарий в PR видит
    тот, кто в этот PR смотрит; общий канал — единственное место, где состояние
    всей связки видно сразу. От дублей защищает маркер в самом issue, а не
    память процесса: состояние диспетчера переживает не всё.
12. Диспетчер отдельным комментарием просит поревьюить новый SHA — по
    умолчанию `@codex review` (`OBOROT_BRIDGE_REVIEW_REQUEST_COMMAND`, пусто —
    не просить). Один комментарий на SHA; от дублей защищает маркер в самом PR,
    а не память процесса. Круг замыкается.
13. Merge не делает никто. Слияние — решение владельца, всегда.

Состояния в отчётах: `PUSHED`, `TESTS_FAILED`, `NO_CHANGES`, `CLAUDE_FAILED`,
`PUSH_REJECTED`, `NEEDS_HUMAN`. Все шесть зеркалируются в issue-канал;
промежуточные (`WORKING`, `CLEAN`, `APPROVED`) — нет, там нужна сводка, а не
поток.

### Почему круг замыкается просьбой, а не push

Шаг 12 раньше звучал как «новый SHA снова будит Codex» — и это было
предположением, а не проверенным фактом. 23.08.2026 оно не подтвердилось:
коммит `1c7d616` уехал в ветку открытого PR #7, и нового ревью не появилось;
комментарий `@codex review`, оставленный руками, запустил ревью сразу.

Цена ошибки здесь несимметричная. Лишняя просьба — это один комментарий под PR.
Пропущенное пробуждение — это молчаливо вставший круг, причём сторож о нём не
скажет ни слова: он ищет **ревью без ответа**, а тут нет и самого ревью. Пока
причина молчания на стороне облака неизвестна, дешевле разбудить явно.

### Куда переезжают замечания

Поле `commit_id` у inline-замечания не постоянное. GitHub переставляет
комментарий на свежий коммит, если строка в файле не изменилась: замечание
`3839314973` в PR #7 было оставлено к ревью коммита `193602bf`, а после push
коммита `1c7d616` получило `commit_id` нового коммита — при `original_commit_id`
и `pull_request_review_id` от старого. У самого ревью `commit_id` не переехал.

Из-за этого диспетчер, сравнивавший `commit_id` замечания с HEAD, видел четыре
уже отработанных замечания как четыре новых: заново будил Claude чинить
починенное и тратил на это попытку из трёх. Сторож на тех же данных объявил бы
тревогу по SHA, к которому у ревьюера претензий не было.

Устойчивая привязка: `pull_request_review_id` → `commit_id` ревью, иначе
`original_commit_id`, и только для payload без обоих полей — `commit_id`.
Диспетчер (`inline_anchor_sha` в `tools/agent-bridge/bridge.py`) и сторож
(`anchorSha` в `.github/workflows/agent-watchdog.yml`) обязаны считать
одинаково: разойдутся — сторож начнёт ругаться на SHA, к которому у диспетчера
претензий нет, и его перестанут читать.

Если inline-замечаний больше, чем `MAX_INLINE_COMMENTS` (по умолчанию 60), за
прогон уезжает первая порция, а остаток **остаётся необработанным** и приходит
следующим циклом. Обработанными помечаются ровно те замечания, что ушли в
запрос: считать сделанным то, чего модель не видела, — худший из возможных
способов «закрыть» ревью.

Команда тестов у диспетчера совпадает с CI намеренно. Диспетчер, который
«краснее» CI, бесполезен — его отчёты перестают читать. Диспетчер, который
«зеленее», опаснее вдвойне: он пушит в ветку, из которой прод обновляется сам.

## Что нужно один раз настроить

**На стороне GitHub.** Нативный Codex Cloud Code Review подключён к
репозиторию и настроен ревьюить push — это уже сделано. Никаких secrets
создавать не нужно: их в этой схеме нет вообще. На push он отзывается не
всегда, поэтому новый SHA дополнительно сопровождается просьбой
`@codex review` — её публикует диспетчер.

**На машине владельца.**

```bash
gh auth status                     # должен быть авторизован
gh auth setup-git                  # чтобы push не спрашивал пароль у фоновой задачи
claude --version                   # должен быть авторизован подпиской Claude Max
tools/agent-bridge/run.sh health   # сводная проверка, код возврата 0
```

`gh auth setup-git` обязателен. Без credential helper `git push` попросит пароль,
а под LaunchAgent отвечать некому — цикл будет падать каждую минуту.

Тестам нужен интерпретатор с зависимостями проекта. У системного `python3` их
нет, и набор упал бы на первом импорте — а выглядело бы это как «правка сломала
тесты», самая дорогая в разборе ложная тревога. Соберите venv из того же
lock-файла, что ставят CI и деплой, и укажите его в настройках:

```bash
python3 -m venv ~/.local/state/oborot-agent-bridge/venv
~/.local/state/oborot-agent-bridge/venv/bin/pip install -r requirements.lock
echo 'OBOROT_BRIDGE_TEST_PYTHON=~/.local/state/oborot-agent-bridge/venv/bin/python' \
  >> ~/.config/oborot-agent-bridge/config.env
```

Venv надо пересобирать при каждом изменении `requirements.lock`.

Затем — сухой прогон и один настоящий цикл руками:

```bash
tools/agent-bridge/run.sh poll --once --dry-run
tools/agent-bridge/run.sh poll --once
```

И только потом установка автоматики:

```bash
tools/agent-bridge/install.sh
```

`install.sh` ставит per-user LaunchAgent `com.oborot.agent-bridge`, который
запускает один цикл примерно раз в минуту и при входе в систему. Per-user, а не
системный демон, потому что диспетчеру нужны ключи авторизации `gh` и `claude`
из связки ключей этого пользователя: демон от root до неё не дотянется.
LaunchAgent переживает закрытие терминала и logout — этим он и отличается от
«оставить процесс в открытом окне».

Снять: `tools/agent-bridge/uninstall.sh` (с `--purge` — вместе с состоянием).

Настройки — `~/.config/oborot-agent-bridge/config.env`, образец в
`tools/agent-bridge/config.env.example`. Секретов там нет и быть не должно.

**Логин ревьюера.** По умолчанию диспетчер слушает
`chatgpt-codex-connector[bot]`. Если нативный Codex подписывается в этом
репозитории иначе, посмотрите фактический логин и впишите его:

```bash
gh api repos/chernim-cherno-analytics/oborot-saas/pulls/<N>/reviews --jq '.[].user.login'
```

Пока логин не совпадает, диспетчер молчит — и это правильное поведение: чинить
код по замечаниям неизвестно кого он не будет.

## Ограничения, зашитые в код

Три попытки на один SHA, дальше `NEEDS_HUMAN` и остановка. Если три захода не
закрыли замечание, четвёртый его тоже не закроет, а историю PR испортит. Новый
коммит в ветке снимает ограничение сам.

Никогда `merge`, `rebase`, `--force`, `--force-with-lease`. Диспетчер работает в
detached HEAD своего клона: локальной ветки нет, значит нет и соблазна её
«подтянуть». Публикация — единственной командой `git push origin
HEAD:refs/heads/<ветка>`. Отклонённый push не форсится: раз ветка уехала вперёд,
там кто-то работал, и следующий цикл начнёт с её актуального SHA.

Никогда merge Pull Request — ни при одобрении, ни по таймауту.

Только свои ветки `claude/*` и только PR, у которых head-репозиторий совпадает с
основным. Пушить в ветку форка — не наша роль.

Правки в `.github/workflows/**` и `tools/agent-bridge/**` откатываются до
коммита: автоматика не переписывает автоматику, иначе один неудачный прогон
ломает механизм, которым его чинят.

`claude` запускается с `--allowedTools Read,Edit,Write,Glob,Grep`. Bash не
разрешён.

Ни один секрет не читается и не передаётся. Диспетчер не принимает API-ключей:
доступ к GitHub берётся из авторизованного `gh`, доступ к модели — из
авторизованного `claude`. Всё, что похоже на токен, вычищается из журнала и из
комментариев перед записью — `gh` и `git` могут выплюнуть токен в тексте ошибки,
а журнал и комментарий переживут инцидент надолго.

Рабочая копия у диспетчера своя, в каталоге состояния. Каталог человека он не
трогает: в своей копии он делает `checkout --force` и `clean -fd`.

## Восстановление

| Симптом | Что произошло | Что делать |
|---|---|---|
| Ревью Codex висит, ответа нет, в PR появился комментарий `oborot-watchdog` | машина спит, выключена или без сети | разбудить машину; `run.sh health` |
| `run.sh health` ругается на `claude` или `gh` | LaunchAgent не нашёл бинарник или сессия разлогинена | `gh auth login`, переавторизовать `claude`, при нужде задать `OBOROT_BRIDGE_CLAUDE_BIN` / `OBOROT_BRIDGE_GH_BIN` |
| В PR `TESTS_FAILED`, а в хвосте `ModuleNotFoundError` | у интерпретатора тестов нет зависимостей проекта | пересобрать venv из `requirements.lock` и задать `OBOROT_BRIDGE_TEST_PYTHON` |
| В PR `TESTS_FAILED` | правка внесена, но тесты не прошли; в ветку ничего не отправлено | прочитать хвост тестов в комментарии; починить руками или уточнить замечание |
| В PR `NO_CHANGES` | модель не изменила ни файла — замечание требует решения человека | ответить в PR по существу замечания |
| В PR `PUSH_REJECTED` | ветка уехала вперёд | ничего; следующий цикл начнёт с актуального SHA |
| В PR `NEEDS_HUMAN` | три попытки на один SHA исчерпаны | решение человека. Перезапуск не поможет — новый коммит в ветке снимет ограничение |
| Диспетчер «застрял» | прогон идёт (`claude` + тесты — до получаса) | `run.sh status` покажет «прогон сейчас: идёт». Блокировка снимается сама при завершении процесса |
| Всё сломалось | — | `uninstall.sh`, разобраться, `install.sh`. Состояние при этом сохраняется: стирать улики вместе с автоматикой — худшее из решений |

Диагностика:

```bash
tools/agent-bridge/run.sh health
tools/agent-bridge/run.sh status --remote
tools/agent-bridge/run.sh logs -n 100
```

Состояние — `~/.local/state/oborot-agent-bridge/`: `state.json` (попытки и
обработанные ревью), `bridge.log`, `lock`, `checkout/`, логи launchd. Вне
рабочей копии специально: копию диспетчер сам же и чистит, а счётчик попыток
обязан пережить чистку — иначе цикл «попытка — сброс — попытка» стал бы
бесконечным.

## Стоимость

**Платных вызовов API в этой схеме нет.** Ни `OPENAI_API_KEY`, ни
`ANTHROPIC_API_KEY` не существует, и оба удалены из требований.

Ревью — по подписке ChatGPT/Codex, в пределах её лимитов. Правки — по подписке
Claude Max, в пределах её лимитов; каждый прогон диспетчера расходует ту же
квоту, что и обычная работа в Claude Code. Отсюда потолок в три попытки и
пропуск пустых ревью: и то, и другое — прямая экономия квоты, а не формальность.

GitHub Actions: остался один watchdog, раз в час, десяток секунд на прогон.
Моделей он не вызывает. Права у него ровно два: `issues: write` — написать
комментарий, `pull-requests: read` — прочитать PR и ревью, ради которых всё
затевалось. Второе выписано явно, потому что блок `permissions` обнуляет всё
неперечисленное, и без него сторож падал бы на 403 ещё до первой проверки.
Чистое ревью («no issues found» и подобное, в том числе без inline-замечаний)
он распознаёт тем же признаком, что диспетчер, и тревогу по нему не поднимает.
На публичном репозитории Actions бесплатны, на приватном это единицы минут в
месяц.

Локально расходуется время машины: один цикл — `claude` плюс полный набор
тестов, до получаса. Опрос вхолостую — доли секунды, несколько запросов к API
GitHub раз в минуту.

## Как проверить, что канал живой

Наличие файлов ничего не доказывает. Канал называется `HEALTHY` только после
сквозного прогона:

1. Ветка `claude/agent-loop-smoke` и маленький PR с заведомой мелочью.
2. Нативный Codex оставляет ревью с замечанием к точному SHA.
3. Диспетчер в течение нескольких минут отвечает комментарием `PUSHED`, в
   ветке появляется новый коммит, тесты в отчёте зелёные.
4. Новый SHA снова получает ревью Codex.
5. Ветка и PR удаляются после проверки владельцем.

До этого прогона состояние канала — `DEGRADED`.
