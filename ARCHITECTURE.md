## 1. Стек и границы системы

```
                    ┌────────────────────────────────┐
  МойСклад ────────►│  ms_client (httpx, async)      │
  JSON API 1.2      │  ms_sync (потоки в веб-процессе)│
  Vendor API 1.0    │  ms_writeback / ms_vendor      │
                    └──────────────┬─────────────────┘
                                   │
  Браузер ──HTTP──► FastAPI ──► analytics / order_planner ──► SQLAlchemy ──► SQLite|PostgreSQL
                       │                    ▲
                       │                    └── кэш снапшота в памяти процесса (TTL 600 с)
                       └──► Jinja2 ──► 23 шаблона (12 — самостоятельные HTML)
                       └──► APScheduler (в том же процессе): 06:00 МСК синк+дайджест, ежечасный догон
                                   │
  Telegram Bot API ◄───────────────┘
```

Внешних зависимостей всего три: МойСклад, Vendor API МойСклада, Telegram.
Ни очередей, ни Redis, ни объектного хранилища, ни почты.

## 2. Сборка приложения

`app/main.py` создаёт `FastAPI(docs_url=None, redoc_url=None)` и подключает пять
роутеров: `api` → `connect` → `extra` → `ms_vendor` → `ms_app`. **Порядок значим**:
в `api.py` есть заглушка `POST /api/connect/moysklad`, и `routes_connect.py`
на импорте **удаляет её из чужого роутера** мутацией `app.api.router.routes`.
Перестановка `include_router` меняет поведение — это скрытая связность.

Кроме роутеров, `main.py` сам регистрирует ~20 маршрутов (страницы, формы входа,
`/api/account*`).

**Middleware ровно один** — `_security_headers_and_csrf`:
* CSRF: для `POST/PUT/PATCH/DELETE` на `/api/*` требует **наличия** заголовка
  `X-Oborot-CSRF` (значение не проверяется). Токенов нет.
* CSP: `frame-ancestors 'self' https://online.moysklad.ru`.

CORS-middleware в проекте **нет вообще**. Это делает «проверку наличия заголовка»
работоспособной защитой: кросс-доменный запрос с кастомным заголовком требует
preflight, одобрять его некому. Но защита держится на отсутствии одной строки кода:
добавление `CORSMiddleware` с `allow_credentials=True` отключит её молча.

**Два startup-хендлера, в порядке регистрации:**
1. `scheduler.start` — планировщик поднимается **до** миграций;
2. `main._startup` — `check_proxy_config()` (fail-fast) → `init_db()` →
   пять `ensure_schema()` из разных модулей → `reset_stale_running()`.

Ещё одна миграция (`lessons.ensure_schema`) вызывается **на импорте** `api.py`,
хотя комментарии в трёх местах утверждают, что миграции с импорта убраны.

## 3. Слои: где они есть и где их нет

Модули названы по ролям (`analytics`, `order_planner`, `ms_*`, `routes_*`), и
на верхнем уровне разделение осмысленное. Ниже — фактические нарушения границ,
проверенные по коду:

| Нарушение | Конкретно |
|---|---|
| Доменная логика в роутерах | `api.round_to_batch`, `api.production_conditions`, `api.apply_production_rules`, `api._order_fingerprint`; `routes_extra.moq_conflict_note`, `apply_replenish_drafts`, `replenish_as_on_screen` |
| Роутер импортирует приватное имя другого роутера | `routes_extra` → `from app.api import _require_known_base, apply_production_rules, production_conditions` |
| ORM-модель объявлена в роутере | `BillingRequest` живёт в `routes_extra.py`; из-за этого удаление организации в `main.py` импортирует роутер |
| DDL размазан по шести модулям | `models`, `exclusions`, `ms_sync`, `ms_writeback`, `ms_vendor`, `lessons` — каждый владеет своими `ALTER TABLE` |
| Интеграция открывает сессии и дёргает домен | `ms_sync` вызывает `SessionLocal()` напрямую, внутри рабочего потока импортирует `notify` и вызывает `analytics.invalidate` |
| Планировщик содержит SQL | `scheduler` сам строит `select(...).join(...)` |
| Persistence в оркестраторе | `main._purge_org` — жёстко зашитый список из 20 моделей |
| Два независимых рендер-хелпера | `main._authed_page` и `routes_extra._authed_page` кладут **разные** контексты (последствия — в PRODUCT_STATUS §2) |

Правильный образец в проекте тоже есть и его стоит отметить: `order_planner.plan_order(snap, brief, ctx)` — **чистая функция без доступа к БД**. Это единственная явная граница «сбор данных ↔ доменный расчёт» во всём коде.

## 4. База данных

**Движок.** SQLAlchemy 2.0, `create_engine(DATABASE_URL)`, пул не настраивается.
`DATABASE_URL` по умолчанию `sqlite:///oborot.db`. Сессия на запрос через
зависимость; коммит/роллбэк — на совести роута. **Драйвера PostgreSQL в
`requirements.txt` нет**, хотя README предписывает `postgresql+psycopg://`.

**Факт, который стоит держать в голове весь аудит: боевая база — SQLite**
(файл ~24 МБ на VPS). README, комментарии в коде и часть решений написаны так,
будто в проде PostgreSQL. Это расхождение объясняет, почему дефект
PostgreSQL-совместимости прожил в коде долго: на нём просто никто не работал.

**Схема** создаётся `Base.metadata.create_all()` с ретраями на «занято/уже есть».

**Миграции — самописные, два механизма:**
* `run_migration_step(sql)` — один SQL в своей транзакции; «уже сделано»
  распознаётся **по подстроке в тексте ошибки** (`duplicate column`, `already exists`…);
  **журнала не ведёт**, идемпотентность обеспечивает предварительная интроспекция колонок;
* `run_migration_once(flag, work)` — **есть журнал**: таблица `migration_flags`.
  Используется ровно **двумя** миграциями из всех.

Итого: состояние схемы боевой БД восстанавливается только интроспекцией живой базы.
Порядка миграций, отката и связи со схемой в коде нет. Alembic отсутствует.

**Таблиц 26.** Ключевые: `users`, `orgs`, `memberships`, `connections`,
`warehouses`, `products`, `stock_days`, `warehouse_stock`, `sales`, `ordered_qty`,
`productions`, `production_assign`, `production_orders`, `order_plans`,
`replenish_drafts`, `sync_state`, `notify_settings`, `sku_hidden`,
`sku_discounts`, `sku_category_overrides`, `category_merges`, `user_lessons`,
`user_prefs`, `user_hints_seen`, `billing_requests`, `migration_flags`.

**Индексы объявлены только четыре** (`products(org,base)`, `stock_days(org,date)`,
`sales(org,date)`, `sales(org,product)`) плюс `index=True` на `org_id` в семи
таблицах. Составные PK играют роль уникальности ещё в десяти.

**Внешние ключи** объявлены везде, но **без `ondelete`**, и **ни одного
`relationship()`** — все связи через ручные join'ы. В SQLite FK по умолчанию
не проверяются, `PRAGMA foreign_keys` нигде не включается.

**JSON-поля** — обычный `Text` со строкой JSON, не нативный тип: `orgs.settings_json`,
`productions.stages_json`, `production_orders.items_json`, `sync_state.stats_json`,
`order_plans.{brief,computed,result}_json`. По `stats_json` идёт **поиск `LIKE`**
(`orgs_with_resume_point`) — то есть JSON уже используется как индексируемое поле.

Отдельная ловушка: `orgs.settings_json` читают **два разных читателя** — свойство
`Org.settings` (возвращает только три ключа из дефолтов) и `analytics.extra_settings`
(возвращает ещё десяток). Уже приводило к потере данных: сохранение настроек
затирало правило распределения по производствам (инцидент 22.08, исправлено —
запись теперь идёт поверх сырого JSON).

### Не установлено
* Тип боевой БД и фактический `DATABASE_URL`.
* Применены ли на боевой БД все ALTER'ы (журнала нет).
* Настройки пула соединений (зависят от версии и драйвера).

## 5. Аутентификация, авторизация, секреты

**Сессия** — подписанная (не шифрованная) кука `oborot_session` с
`{user_id, org_id}`, `HttpOnly`, срок 7 дней, `Secure` в проде,
`SameSite=Lax` обычно и `SameSite=None` во встроенном режиме МойСклада.
Серверного хранилища сессий нет ⇒ **отозвать сессию нельзя**: смена пароля
не разлогинивает другие устройства (в UI это написано честно).

**Роли** — `owner`/`member`, проверяются единственной зависимостью
`require_owner_api`. Проверка применена **непоследовательно**: часть ручек,
меняющих данные всей организации, доступна `member` (список — TECH_DEBT SEC-2).
Страничные роуты роль не проверяют вовсе; фронт узнаёт её из API.

**Пароли** — bcrypt с дефолтной стоимостью; ограничение 72 байта проверяется
явно с человеческой ошибкой (а не тихим усечением). Минимум 8 символов.
**Восстановления пароля нет** — почтовой инфраструктуры в проекте нет вообще;
единственный путь — письмо на личную почту владельца, захардкоженную в коде.

**Лимитер входа** — свой класс, два экземпляра (по аккаунту 5/300 с, по IP 20/300 с),
хранилище — словарь **в памяти процесса**. Окно фиксированное: заблокированный
ключ нельзя продлить чужими попытками, а верный пароль всегда пропускает —
иначе, зная чужой e-mail, можно было держать клиента заблокированным вечно.
Разбор `X-Forwarded-For` управляется `OBOROT_TRUSTED_PROXY_HOPS`: при
`OBOROT_ENV=prod` переменная **обязательна**, иначе приложение не стартует
(намеренный fail-fast: без неё защита молча выключается). Требует запуска
uvicorn с `--no-proxy-headers`.

**Секреты.** Один мастер-секрет `OBOROT_SECRET`; из него выводятся два ключа
по назначению — подпись сессий и Fernet для токенов интеграций. Вывод — **одинарный
`sha256(secret|purpose)`**, не KDF: без соли, без растяжения, энтропия секрета
не проверяется. Ротации нет: смена секрета делает все сохранённые токены МойСклада
нечитаемыми (`decrypt_token` вернёт `None`), и это нигде не обрабатывается как
сценарий. Шифруется ровно одно поле — `connections.token_enc`.
`MS_APP_SECRET` и `OBOROT_TG_BOT_TOKEN` берутся из env напрямую, без обёртки.

### Моя оценка
Схема аутентификации для MVP сделана аккуратно и с пониманием атак (fail-fast
на прокси-конфиге, «мягкий» лимитер, явная ошибка на 72 байтах — всё это
не типовые решения, а следы разбора конкретных сценариев). Слабые места не в
механизмах, а в **отсутствии отзыва сессий**, **непоследовательности проверки роли**
и **отсутствии ротации ключей**.

## 6. Фон, планировщик, конкурентность

**Планировщик** — APScheduler `BackgroundScheduler` **внутри веб-процесса**,
хранилище задач — память. Два джоба: `daily-sync-digest` (06:00 МСК: последовательный
обход организаций, инкремент + Telegram-дайджест) и `hourly-catchup-sync`
(каждый час в :30: организации, чей синк старше 26 ч, плюс все с точкой
продолжения). Идемпотентность старта — флаг **в памяти процесса**.

**Каждый синк — отдельный `threading.Thread(daemon=True)` в том же веб-процессе**,
внутри — свой `asyncio.run()`. Реестр потоков — словарь в памяти.
Точек запуска шесть (кнопки в UI, смена токена, lifecycle-PUT от МойСклада, два джоба).

**Многопроцессность ломает разом семь механизмов** — все внутрипроцессные:
реестр потоков синка, флаг планировщика, кэш аналитики и его инвалидация,
кэш типов цен, карта поставщиков, лимитер входа, анти-replay для Vendor JWT.
Прод рассчитан на **один воркер**, но это **нигде не форсируется кодом** — только
комментариями и README. При этом соседний, менее опасный параметр
(`OBOROT_TRUSTED_PROXY_HOPS`) fail-fast'ом защищён. Асимметрия странная.

Отдельно: `reset_stale_running()` на **каждом** старте процесса переводит **все**
`sync_state.state='running'` в `error`. При двух воркерах или rolling-деплое
новый процесс объявляет оборванным синк, реально идущий в другом живом процессе.

**Единственный межпроцессный лок во всей системе** — значение `pending:<epoch>`
в `production_orders.ms_doc_href`, захватываемое условным UPDATE с проверкой
`rowcount`, TTL 180 с. Он защищает отправку заказа в МойСклад.

## 7. Интеграция с МойСклад

### Транспорт (`ms_client.py`)
Один `httpx.AsyncClient` на подключение, таймаут 90 с на все фазы, Bearer-токен.
Лимиты: скользящее окно **45 запросов / 3 с**, семафор параллельности **5**,
отдельный «тяжёлый» семафор **3** для `report/stock/all`, общий cool-down до 10 с
после 429. Ретраи: до **10** повторов на `{429,500,502,503,504}` и транспортные
ошибки; backoff — уважает заголовок `X-Lognex-Retry-TimeInterval`, дальше
экспонента с джиттером и потолком 60 с (худший случай ≈ 300 с на один запрос).
Пагинация: 1000 строк, но **100** при `expand=positions` (ограничение МС).

Зашитые в клиент особенности API документированы и точны: `moment` в отчёте
остатков работает **только внутри `filter=`**, при `expand=positions` максимум
100 строк, все цены — в копейках.

**Замечание:** два семафора независимы, общего потолка нет — теоретически
5 + 3 = 8 одновременных запросов при документированном лимите МС в 5.
Сегодня фазы синка не пересекаются, поэтому проблема латентная.

### Что читается и куда пишется
Ассортимент → `products` (вариант = `base_name` родителя + размер из характеристики
или из финальных скобок имени); контрагенты → `products.supplier`;
`report/stock/all` по каждой дате и складу → `stock_days` + `warehouse_stock`;
четыре типа документов (розница/опт, продажи/возвраты) → `sales`;
`purchaseorder` → `ordered_qty.ms_qty`.

**Цены** — три величины: `sale_price` (тип цены выбирается в настройках, иначе
по подсказкам «цена продажи/розниц/sale/retail», иначе первая),
`cost_price` = `buyPrice`, `cost_full` = выбранный тип «себестоимость».
Различие принципиально: у бренда со своим пошивом `buyPrice` содержит **только
пошив без ткани**, и деньги по нему занижены вдвое. Отсюда `cost_full`.

### Синхронизация
Два режима, `initial` и `incremental`, с автоматическими промоушенами:
любой запуск превращается в продолжение первичной загрузки, если она была
прервана (инкремент поверх короткой истории дал бы битую оборачиваемость).

Первичная загрузка **прогрессивная**: сначала сегодня, потом окно 30 дней →
**finalize-lite** (сервис объявляется рабочим, `state` остаётся `running`) →
остальные ~335 дней чанками по 30 дат **назад**, с инвалидацией кэша после
каждого чанка. Пользователь начинает работать через минуты, а не через час.

**Резюмирование** держится на трёх ключах в `stats_json`: `history_loaded_from/to`
(границы загруженного), `resume_fp` (отпечаток «набор складов + глубина» —
не совпал, значит продолжать нельзя, нужна пересборка), `needs_full_rebuild`.
Отдельная тонкость, решённая аккуратно: при загрузке чанков **назад**
левая граница каждого чанка получает «граничную заплатку» с явными нулями,
чтобы результат совпадал с прямым хронологическим проходом — этот инвариант
проверяется тестом.

**Явные нули**: позиция, у которой остаток был > 0 и которая исчезла из отчёта,
получает строку `qty=0`. Правило самоизлечивающееся.

**Продажи всегда переписываются диапазоном** (удалить окно → вставить заново),
ширина окна в инкременте = фактический простой + 1 день, не фиксированные 3 дня.

**Черновики документов** (`applicable=False`) отбрасываются — и в продажах,
и в заказах поставщику.

### Машина состояний
`idle → running → done|error`. Поля: стадия, прогресс, человекочитаемый `detail`,
`stats_json`, `error`, `fail_streak`, `alerted_streak`. Ошибки классифицируются
на `token` / `transient` / `internal`, наружу отдаётся русский текст без внутренностей.
Право на Telegram-алерт выдаётся **атомарным UPDATE** ровно один раз на серию.
Фоновая догрузка истории у уже работающего сервиса намеренно не считается
«падающим синком».

Это одна из самых продуманных частей системы.

### Обратная запись
`POST /api/orders/{id}/push-to-ms` (owner) создаёт в МойСкладе **«Заказ поставщику»**
(не «Заказ на производство» — тот требует техкарту и есть не на всех тарифах).
Лок `pending:` берётся **до** сетевых вызовов; повторная отправка при заполненной
ссылке → 409. Двойной счёт «едет к нам» разведён явно: заказ, отправленный в МС,
локальный счётчик не двигает.

**Здесь же — самый серьёзный найденный мной дефект интеграции.** `POST` идёт через
тот же механизм ретраев, что и `GET`: при таймауте `POST /entity/purchaseorder`
документ в МойСкладе может быть создан, а ответ не дойти — и клиент **повторит
запрос**, создав второй финансовый документ. Ключа идемпотентности нет, поиска
уже созданного по описанию нет. Наш `pending:`-лок здесь не помогает: он защищает
от двух наших запросов, а не от двух документов внутри одного. То же для создания
контрагента «Производство». Подробности и соседний сценарий (падение `commit`
после успешного push) — в TECH_DEBT, DATA-2 и DATA-3.

### Vendor API и встроенный режим
Полный lifecycle приложения каталога МойСклад: `PUT` (Install/TariffChanged/Resume)
создаёт организацию, кладёт присланный токен, подхватывает все склады и запускает
первичный синк — **пользователь не вводит ничего**; `DELETE` (Uninstall/Suspend)
переводит организацию в `suspended` (данные и вход сохраняются, планировщик
её пропускает). JWT HS256 в обе стороны, алгоритм зафиксирован, `exp`/`iat`
обязательны, возраст ≤ 300 с, одноразовый `jti`, защита от отражения своего же
токена. SSO через `?contextKey` создаёт пользователя с техническим e-mail и
ставит куку с `SameSite=None`.

**Продуктовое следствие, которое стоит проверить в первую очередь:** встроенный
режим поддержан только на шести вспомогательных экранах (вход, регистрация,
онбординг, настройки, аккаунт, тарифы). Девять основных рабочих страниц про него
не знают вовсе — см. PRODUCT_STATUS §3. Если каталог МойСклада — якорный канал
продаж, это дыра в самом канале.

## 8. Кэширование

Кэш ровно один: снапшот аналитики, `dict[org_id → (deadline, данные)]`
**в памяти процесса**, TTL 600 с. Ключ — только `org_id` (ни версии данных,
ни настроек). Инвалидация — ручной вызов `analytics.invalidate(org_id)` из
десятков мест; единого write-хука нет. Защиты от stampede нет: при параллельных
запросах снапшот считается несколько раз, побеждает последний записавший.
Размер не ограничен.

При нескольких воркерах кэш и инвалидация процесс-локальны: запись через воркер A
не сбросит кэш у B, C, D — до 10 минут разных чисел на одной странице.

## 9. Переменные окружения

Обязательные в проде: `OBOROT_ENV=prod`, `OBOROT_SECRET` (без него — ошибка
при первом использовании, **не** на старте), `OBOROT_TRUSTED_PROXY_HOPS`
(fail-fast на старте), `DATABASE_URL`.
Поведенческие: `SCHEDULER_ENABLED`, `MS_MAX_RETRIES`, `MS_REPORT_PARALLEL`,
`MS_CHUNK_PAUSE`, `HISTORY_DAYS`, `SYNC_DAYS_BACK`, `INITIAL_WINDOW_DAYS`,
`STOCK_CHUNK_DATES`.
Интеграционные: `MS_BASE_URL`, `MS_APP_ID`, `MS_APP_UID`, `MS_APP_SECRET`,
`MS_VENDOR_API_BASE`, `OBOROT_TG_BOT_TOKEN`, `OBOROT_TG_BOT_NAME`, `TG_API_BASE`,
`OBOROT_SUPPORT_URL`, `OBOROT_SUPPORT_EMAIL`.

Централизованного settings-объекта нет, каждый модуль читает `os.environ` сам
**на уровне модуля** (значения фиксируются на импорте). `.env.example` нет.
`HISTORY_DAYS` и `SYNC_DAYS_BACK` разбираются `int()` **без обработки исключения** —
мусор в переменной роняет импорт модуля.

## 10. Развёртывание и наблюдаемость

В репозитории: `run.py` — `uvicorn` на `127.0.0.1:8000`, один процесс, порт не из env.
Рекомендуемая прод-команда есть **только в комментарии** к `auth.py`.
Нет: Dockerfile, compose, Procfile, конфигов nginx/systemd, CI, `docs/`
(README ссылается на несуществующий `docs/DEPLOY.md`), `.env.example`,
пинов версий и lock-файла.

**Наблюдаемости практически нет.** Конфигурации логирования нет вообще
(ни `basicConfig`, ни `dictConfig`) — куда и на каком уровне пишутся
`log.warning`/`log.exception`, определяет хостинг. В `ms_sync.py` семь голых
`print()`. Health-эндпоинтов нет. Метрик нет. Sentry нет. Единственный
канал наблюдения за системой — Telegram-алерт о втором подряд упавшем синке
и «табло свежести» в интерфейсе.

### Установлено вне репозитория (со слов эксплуатации, не из кода)
* Прод — обычный VPS, systemd-юнит `oborot`, `ExecStart=…/python run.py`,
  то есть **один процесс** (требование одного воркера де-факто выполняется).
* Впереди nginx, `X-Forwarded-For` формируется через `$proxy_add_x_forwarded_for`,
  переменная `OBOROT_TRUSTED_PROXY_HOPS=1` выставлена.
* База — SQLite `/opt/oborot/data/oborot.db`, ~24 МБ.
* Перед последним деплоем сделана **ручная** копия файла базы.

### Не установлено
* Есть ли **регулярный** бэкап и проверялось ли восстановление
  (известна одна ручная копия перед деплоем — это не процедура).
* Реальные версии установленных зависимостей.
* Есть ли мониторинг самого VPS.

## 11. Точки отказа интеграции (сводка)

Развёрнуто — в TECH_DEBT. Кратко, по убыванию моей оценки риска:

1. Повтор `POST` при таймауте создаёт **дубликат заказа поставщику** в МойСкладе.
2. Провал `commit` после успешного push оставляет вечный `pending:` и теряет ссылку.
3. Разрыв между стиранием истории остатков и перезаписью продаж в первичном синке:
   падение между ними оставляет **1 день остатков и год продаж** — оборачиваемость
   вырастает в десятки раз, а сервис остаётся «активным».
4. Гонка отправки заказа с импортом «Заказов поставщику» обнуляет «едет к нам».
5. Частичное сопоставление позиций при отправке систематически занижает «едет к нам».
6. Товары, созданные в МС между чтением ассортимента и отчётом остатков, молча
   теряются на весь прогон (наружу — только счётчик).
7. История **никогда не перечитывается**: документ, проведённый задним числом
   за пределами окна инкремента, не попадёт в систему никогда. Механизма сверки с МС нет.
8. Ошибка справочника контрагентов молча **затирает всех поставщиков**, ломая
   правило распределения по производствам.
9. Опечатка/переименование выбранного типа цены обнуляет `cost_full` без предупреждения.
