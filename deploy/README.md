# Развёртывание

Прод: обычный VPS, systemd-юнит `oborot`, один процесс
(`/opt/oborot/venv/bin/python run.py`), база — файл SQLite
`/opt/oborot/data/oborot.db`.

## Выкатить

На сервере, от root:

```bash
cd /opt/oborot/app-src
bash deploy/deploy.sh              # текущая вершина main
bash deploy/deploy.sh 0fd3783      # конкретный коммит
```

(Через `bash`, а не `./`: файлы, залитые в репозиторий веб-интерфейсом GitHub,
теряют признак исполняемого. `chmod +x deploy/deploy.sh` один раз на сервере
делает вариант `./deploy/deploy.sh` рабочим.)

Скрипт снимет копию базы, переключит рабочую копию на коммит (detached checkout,
не «pull ветки» — поэтому всегда видно, что именно в бою), поставит зависимости,
перезапустит сервис и дождётся `/health/ready`. Не поднялось — печатает логи и
команду отката.

## Откатить

```bash
bash deploy/deploy.sh $(cat /opt/oborot/PREVIOUS_SHA)
```

База при откате **не восстанавливается** и обычно не требует восстановления:
миграции аддитивные, старый код работает на новой схеме. Если всё же нужна —
копии лежат в `/opt/oborot/data/backups/` (хранятся последние 14).

## Что должно быть в /opt/oborot/env

```
OBOROT_ENV=prod
OBOROT_SECRET=<длинный секрет>
OBOROT_TRUSTED_PROXY_HOPS=1     # без неё приложение в проде не стартует
DATABASE_URL=sqlite:////opt/oborot/data/oborot.db
SCHEDULER_ENABLED=1             # ровно на ОДНОМ процессе
OBOROT_COMMIT=<ставит deploy.sh>
OBOROT_SUBSCRIPTION_GATE=1      # НЕ ставить, пока не проставлен paid_until (см. ниже)
```

Приложение рассчитано на **один процесс**: кэш аналитики, лимит попыток входа и
планировщик живут в его памяти. При `WEB_CONCURRENCY > 1` оно намеренно не
стартует — см. `_check_single_process` в `app/main.py`.

## Гейт подписки (D-24)

Выключен, пока в окружении нет `OBOROT_SUBSCRIPTION_GATE=1`. Включённый гейт
переводит неоплаченные организации в режим «только чтение»: не идут синки
(в том числе ночные), нельзя записать заказ в МойСклад и посчитать план.
Чтение, экспорт, тарифы и заявка на счёт остаются доступны всегда.

**Порядок включения — именно такой:**

1. Посмотреть, кого закроет. Приложение печатает это в лог на каждом старте:
   ```bash
   journalctl -u oborot -n 200 | grep 'гейт подписки'
   # гейт подписки выключен; если включить: active=1 grace=0 readonly=2 (закрылись бы [3, 7])
   ```
2. Проставить «оплачено до» тем, кто платит (дата включительно, `YYYY-MM-DD`):
   ```bash
   sqlite3 /opt/oborot/data/oborot.db \
     "UPDATE orgs SET paid_until = '2026-12-31' WHERE id = 1;"
   ```
   Понимаются три формата: `2026-12-31`, `2026-12-31 00:00:00` (как у соседней
   `trial_ends_at`) и `31.12.2026`. Формат со слэшами намеренно НЕ принимается:
   `01/02/2026` в одной половине мира первое февраля, в другой второе января.
   Значение, которое разобрать не удалось, читается как «не оплачено» — и
   тогда в базе лежит текст, которого не видно запросом `WHERE paid_until IS
   NULL`; искать такие организации надо по строке предпросмотра в логе.
   Организациям из каталога МойСклад (`source = 'ms_app'`) ничего проставлять
   не нужно: их состояние приходит из МС.
3. Перезапустить сервис и **снова** прочитать строку предпросмотра: в списке
   `закрылись бы` должны остаться только те, кого действительно закрываем,
   а строки «состояние подписки не удалось вычислить» быть не должно вовсе —
   это организация с непонятной датой, и до включения флага её надо починить.
4. Только теперь добавить `OBOROT_SUBSCRIPTION_GATE=1` в `/opt/oborot/env`
   и перезапустить. Строка в логе станет `гейт подписки ВКЛЮЧЁН: …`.

Выключается обратно удалением переменной и перезапуском — данные не страдают.

Отметка «счёт выставлен» даёт клиенту 5 календарных дней работы:
```bash
sqlite3 /opt/oborot/data/oborot.db \
  "UPDATE billing_requests SET status='invoiced', invoiced_at=datetime('now') WHERE id = 12;"
```
Если `invoiced_at` забыть, приложение проставит его само при первой встрече —
грейс начнётся позже, но клиент не окажется закрыт из-за нашей забывчивости.

## Чего здесь нет и почему

Ни контейнеров, ни оркестратора, ни отдельного раннера. Машина одна, процесс
один, зависимости — чистый Python: Docker в такой конфигурации не покупает
ничего, кроме ещё одного слоя, который придётся обслуживать.

## Бэкап

`deploy.sh` делает копию **перед каждой выкладкой** — это защита от плохого
релиза, а не резервное копирование. Отдельно нужны: регулярная копия по
расписанию, хранение вне этой машины и **хотя бы одна проверка восстановления**.
Пока восстановление ни разу не проверялось, копию нельзя считать бэкапом.
