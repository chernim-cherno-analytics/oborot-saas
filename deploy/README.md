# Развёртывание

Прод: обычный VPS, systemd-юнит `oborot`, один процесс
(`/opt/oborot/venv/bin/python run.py`), база — файл SQLite
`/opt/oborot/data/oborot.db`.

## Выкатить

На сервере, от root:

```bash
cd /opt/oborot/app-src
bash deploy/deploy.sh              # текущая вершина main
bash deploy/deploy.sh 0fd3783      # конкретный коммит
```

(Через `bash`, а не `./`: файлы, залитые в репозиторий веб-интерфейсом GitHub,
теряют признак исполняемого. `chmod +x deploy/deploy.sh` один раз на сервере
делает вариант `./deploy/deploy.sh` рабочим.)

Скрипт снимет копию базы, переключит рабочую копию на коммит (detached checkout,
не «pull ветки» — поэтому всегда видно, что именно в бою), поставит зависимости,
перезапустит сервис и дождётся `/health/ready`. Не поднялось — печатает логи и
команду отката.

## Откатить

```bash
bash deploy/deploy.sh $(cat /opt/oborot/PREVIOUS_SHA)
```

База при откате **не восстанавливается** и обычно не требует восстановления:
миграции аддитивные, старый код работает на новой схеме. Если всё же нужна —
копии лежат в `/opt/oborot/data/backups/` (хранятся последние 14).

## Что должно быть в /opt/oborot/env

```
OBOROT_ENV=prod
OBOROT_SECRET=<длинный секрет>
OBOROT_TRUSTED_PROXY_HOPS=1     # без неё приложение в проде не стартует
DATABASE_URL=sqlite:////opt/oborot/data/oborot.db
SCHEDULER_ENABLED=1             # ровно на ОДНОМ процессе
OBOROT_COMMIT=<ставит deploy.sh>
OBOROT_SUBSCRIPTION_GATE=1      # НЕ ставить, пока не проставлен paid_until (см. ниже)
```

Приложение рассчитано на **один процесс**: кэш аналитики, лимит попыток входа и
планировщик живут в его памяти. При `WEB_CONCURRENCY > 1` оно намеренно не
стартует — см. `_check_single_process` в `app/main.py`.

## Гейт подписки (D-24)

Выключен, пока в окружении нет `OBOROT_SUBSCRIPTION_GATE=1`. Включённый гейт
переводит неоплаченные организации в режим «только чтение»: не идут синки
(в том числе ночные), нельзя записать заказ в МойСклад и посчитать план.
Чтение, экспорт, тарифы и заявка на счёт остаются доступны всегда.

**Порядок включения — именно такой:**

1. Посмотреть, кого закроет. Приложение печатает это в лог на каждом старте:
   ```bash
   journalctl -u oborot -n 200 | grep 'гейт подписки'
   # гейт подписки выключен; если включить: active=1 grace=0 readonly=2 (закрылись бы [3, 7])
   ```
2. Проставить «оплачено до» тем, кто платит (дата включительно, `YYYY-MM-DD`):
   ```bash
   sqlite3 /opt/oborot/data/oborot.db \
     "UPDATE orgs SET paid_until = '2026-12-31' WHERE id = 1;"
   ```
   Понимаются три формата: `2026-12-31`, `2026-12-31 00:00:00` (как у соседней
   `trial_ends_at`) и `31.12.2026`. Формат со слэшами намеренно НЕ принимается:
   `01/02/2026` в одной половине мира первое февраля, в другой второе января.
   Значение, которое разобрать не удалось, читается как «не оплачено» — и
   тогда в базе лежит текст, которого не видно запросом `WHERE paid_until IS
   NULL`; искать такие организации надо по строке предпросмотра в логе.
   Организациям из каталога МойСклад (`source = 'ms_app'`) ничего проставлять
   не нужно: их состояние приходит из МС.
3. Перезапустить сервис и **снова** прочитать строку предпросмотра: в списке
   `закрылись бы` должны остаться только те, кого действительно закрываем,
   а строки «состояние подписки не удалось вычислить» быть не должно вовсе —
   это организация с непонятной датой, и до включения флага её надо починить.
4. Только теперь добавить `OBOROT_SUBSCRIPTION_GATE=1` в `/opt/oborot/env`
   и перезапустить. Строка в логе станет `гейт подписки ВКЛЮЧЁН: …`.

Выключается обратно удалением переменной и перезапуском — данные не страдают.

### Выставили счёт → пришли деньги: две разные команды

Отметка «счёт выставлен» даёт клиенту 5 календарных дней работы:
```bash
sqlite3 /opt/oborot/data/oborot.db \
  "UPDATE billing_requests SET status='invoiced', invoiced_at=datetime('now') WHERE id = 12;"
```
Если `invoiced_at` забыть, приложение проставит его само при первой встрече —
грейс начнётся позже, но клиент не окажется закрыт из-за нашей забывчивости.

Когда деньги пришли, нужны **обе** строки — и это ровно то место, где раньше
был капкан:
```bash
sqlite3 /opt/oborot/data/oborot.db \
  "UPDATE billing_requests SET status='paid' WHERE id = 12;
   UPDATE orgs SET paid_until='2026-09-30' WHERE id = 1;"
```
Доказательство оплаты для гейта — **`orgs.paid_until`**, а не статус заявки.
Раньше `status='paid'` использовался наравне с `invoiced`, то есть просто
запускал те же пять дней: организация, про которую в нашей же базе написано
«оплачено», закрывалась на шестой день. Теперь отметка `paid` держит доступ
сама по себе, но это страховка, а не замена сроку — при несведённом
`paid_until` в лог идёт предупреждение:

```
организация 1 помечена оплаченной (billing_requests.status='paid'),
но paid_until не продлён — оставляю доступ. Проставьте срок: ...
```

Увидели такую строку — проставьте `paid_until`. Продление на следующий месяц —
это тоже `UPDATE orgs SET paid_until = ...`, отдельного механизма нет.

## Чего здесь нет и почему

Ни контейнеров, ни оркестратора, ни отдельного раннера. Машина одна, процесс
один, зависимости — чистый Python: Docker в такой конфигурации не покупает
ничего, кроме ещё одного слоя, который придётся обслуживать.

## Бэкап

`deploy.sh` делает копию **перед каждой выкладкой** — это защита от плохого
релиза, а не резервное копирование: копия лежит на том же диске и снимается
только в момент деплоя. Регулярная копия и проверка восстановления — два
отдельных скрипта.

### Снять копию

```bash
bash deploy/backup.sh
```

Снимает согласованный снимок через `sqlite3 .backup` (не `cp`: база работает в
режиме WAL, и обычное копирование файла даёт снимок без последних записей —
проверено, в тесте это отдельный пункт), тут же проверяет его
`PRAGMA integrity_check` и пересчётом строк, сжимает и кладёт в
`/opt/oborot/data/backups/` с датой в имени. Хранит последние `BACKUP_RETAIN`
(по умолчанию 14).

Копия, которая не прошла проверку, **удаляется** и в ротацию не попадает.
Это не мелочь: иначе битый файл однажды окажется тем самым «последним
бэкапом», который берут в день аварии.

Переменные: `OBOROT_DB`, `BACKUP_DIR`, `BACKUP_RETAIN`, `BACKUP_REMOTE`.

### По расписанию

```
# /etc/cron.d/oborot-backup
30 3 * * * root /bin/bash /opt/oborot/app-src/deploy/backup.sh >> /var/log/oborot-backup.log 2>&1
15 4 * * 1 root /bin/bash /opt/oborot/app-src/deploy/restore_test.sh >> /var/log/oborot-backup.log 2>&1
```

Ежедневная копия ночью, проверка восстановления — раз в неделю. Проверка
поднимает приложение на порту 8099 и боевой сервис не трогает.

### Зашифрованная копия вне машины

`backup.sh` и `restore_test.sh` оставлены как быстрая локальная страховка перед
деплоем. От потери VPS защищает отдельная пара:

- `backup_offsite.sh` снимает согласованный SQLite snapshot, проверяет его и
  отправляет в уже созданный удалённый restic repository;
- `restore_offsite.sh` действительно скачивает snapshot обратно, запускает на
  нём приложение и проверяет `/health/ready`, не касаясь production БД;
- общий lock не даёт backup и restore drill менять repository одновременно;
- restic шифрует данные до отправки, хранит 14 daily, 8 weekly и 12 monthly.

Одноразовая активация на VPS:

```bash
apt-get install -y restic sqlite3
install -m 600 deploy/backup.env.example /opt/oborot/backup.env
# заполнить RESTIC_REPOSITORY/credentials; repository должен быть вне VPS
set -a; . /opt/oborot/backup.env; set +a
restic init  # один раз, осознанно, не из backup script
install -m 644 deploy/systemd/oborot-*.service deploy/systemd/oborot-*.timer \
  /etc/systemd/system/
systemctl daemon-reload
systemctl enable --now oborot-backup.timer oborot-restore-drill.timer
systemctl start oborot-backup.service
systemctl start oborot-restore-drill.service
```

Секреты лежат только в `/opt/oborot/backup.env` и password file с правами 600.
Локальный backend намеренно запрещён: иначе каталог на том же VPS мог бы
выглядеть как off-site защита. До выбора provider и успешного запуска обоих
services на VPS операционный риск остаётся открытым.

### Проверить восстановление

```bash
bash deploy/restore_test.sh                    # последняя копия
bash deploy/restore_test.sh /path/to/копия.gz  # конкретная
```

Разворачивает копию во **временный файл**, проверяет целостность и содержимое,
поднимает на ней приложение на отдельном порту и ждёт `"db":true` в
`/health/ready`. Боевую базу и боевой сервис не трогает вообще.

Отдельно проверено, что восстанавливается и **старая** копия: приложение
догоняет схему аддитивными миграциями и стартует. Это не теория — настоящая
авария почти всегда выглядит как «развернули бэкап трёхнедельной давности».

### Почему у этих скриптов есть тест

`tests/test_backup.py` гоняет локальную пару по-настоящему: на базе в WAL, на
намеренно повреждённой, на пустой, без клиента `sqlite3`, на битом архиве, на
копии со старой схемой. Аварийные пути скрипта в обычной жизни не выполняются
никогда — они нужны ровно в тот день, когда что-то сломалось, и до этого дня
никто не узнает, что они не работают.

Именно так и было: первая версия `backup.sh` на повреждённой базе умирала
раньше собственной проверки (`sqlite3` возвращает ненулевой код, `set -e`
убивает скрипт прямо на присваивании) — и оставляла битую копию в ротации.
Скрипт при этом синтаксически безупречен и на здоровой базе работает идеально.
Нашлось это только исполнением; тест держит найденное.

`tests/test_backup_offsite.py` отдельно доказывает remote upload, порядок
retention, полный download, запуск приложения на восстановленной базе, запрет
перезаписи production и fail-closed поведение при сбое repository.
