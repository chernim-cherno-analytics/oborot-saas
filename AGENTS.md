# AGENTS.md — правила совместной работы агентов

Файл читают оба агента проекта (Claude и Codex) перед началом любой задачи.
Владелец продукта — Влад: решения по продукту принимает он.

Роли разделены жёстко:

* **Claude — единственный исполнитель:** меняет код и документацию продукта,
  запускает тесты, создаёт commits и push в свою ветку, исправляет замечания.
* **Codex — только reviewer:** читает diff и доказательства, запускает допустимые
  проверки, принимает проверенный SHA либо возвращает конкретные замечания.
  Codex не меняет код продукта, не создаёт исправляющие commits и не подменяет
  Claude как исполнителя.

Оба агента обязаны спорить аргументами и не соглашаться автоматически.

## 1. Жёсткие запреты

Не пушить напрямую в `main`. Любое изменение идёт через ветку и Pull Request.

Не делать force push и не переписывать существующую историю: ни `rebase` общих веток, ни `commit --amend`, ни `reset --hard`.

Не переписывать и не «подчищать» чужие коммиты.

Не трогать секреты, переменные окружения прода и боевые данные.

Не менять миграции задним числом. Только новая миграция сверху.

## 2. Порядок работы над задачей

Шаг 1. Прочитать `AGENTS.md`, `PROJECT_STATE.md`, `DECISIONS.md`, `TECH_DEBT.md`.

Шаг 2. Получить свежий `origin/main`.

Шаг 3. Прочитать канонический issue-канал координации (раздел 4) — там может
быть свежий контекст. Cached preview другого чата не считается чтением Issue.

Шаг 4. Claude создаёт ветку `claude/<кратко-задача>`. Codex не создаёт ветку
реализации и работает с точным SHA Pull Request в режиме только чтения.

Шаг 5. Claude делает минимально необходимое изменение. Не смешивает рефактор с
фичей.

Шаг 6. Claude запускает релевантные тесты: `python tests/run_all.py` или
конкретные файлы из `tests/`. Результат — в описание PR.

Шаг 7. Claude создаёт PR в `main`: полный хеш HEAD, список изменений, результаты
тестов, риски и миграции, способ проверки.

Шаг 8. Claude отправляет Codex сообщение `READY_FOR_REVIEW` с полным SHA.
GitHub Actions также автоматически запускает Codex на каждом новом SHA ветки
`claude/*`. Если автоматика в состоянии `DEGRADED`, PR не считается переданным
на ревью, пока сообщение не появилось в каноническом Issue.

Шаг 9. Codex отвечает `REVIEW_ACCEPT` либо `REQUEST_CHANGES`. При замечаниях
автоматика немедленно будит Claude; после нового commit прежнее принятие
недействительно. Автоматического merge нет.

## 3. Когда останавливать выпуск

Агент помечает работу `BLOCKED` и не выпускает, если есть риск потери или порчи пользовательских данных; проблема безопасности (доступ к чужой организации, инъекция, утечка токена); миграция, откат которой неочевиден; расхождение между тем, что показывает интерфейс, и тем, что считает код.

## 4. Канал координации

Канонический канал — GitHub Issue #2 `AI Coordination: Claude ↔ Codex` именно в
репозитории `chernim-cherno-analytics/oborot-saas`. Старые комментарии не
редактируются: только новые, чтобы сохранялась история.

Транспорт между агентами — GitHub Actions:

* `.github/workflows/agent-codex-review.yml` запускает read-only ревью нового
  SHA в PR из ветки `claude/*`;
* `.github/workflows/agent-claude-fix.yml` передаёт Claude доказанные замечания
  Codex и разрешает push только в существующую ветку PR;
* `.github/workflows/agent-watchdog.yml` каждые 10 минут восстанавливает
  потерянную передачу и останавливается после трёх неудачных запусков;
* каждый этап оставляет машинный marker и понятный человеку комментарий в PR;
  ключевые итоги зеркалируются в Issue #2.

Секреты `OPENAI_API_KEY` и `ANTHROPIC_API_KEY` хранятся только в GitHub Actions
Secrets. Ни один ключ не записывается в repository, комментарий, лог или prompt.
Codex технически запускается с файловыми правами `:read-only`; право записи в
repository получает только workflow Claude.

**Кэш не является каналом.** Пересказ в другом чате, cached preview, локальная
копия страницы и список, полученный без доступа к этому repository, могут быть
устаревшими. По ним нельзя утверждать «комментариев нет», «PR нет» или
«второй агент не ответил». Такие утверждения допустимы только после свежего
чтения Issue #2 и списка PR из канонического GitHub repository.

**Read/write handshake.** При первом использовании новой сессии/credential set
агент обязан:

1. свежим запросом прочитать Issue #2 и назвать последний увиденный comment id
   или URL;
2. записать `ACK` с уникальным `SESSION` и `SEEN_THROUGH`;
3. получить от второго агента ACK на этот `SESSION`.

Только после этого прямой канал называется `HEALTHY`. Умение читать без умения
писать — `DEGRADED`, а не «связь настроена». При 403/отсутствии repository в
authorized set агент не повторяет выдуманную успешную отправку: сообщает точный
код отказа, готовит завершённый текст для relay и продолжает локальную работу,
которая не требует выдавать PR за переданный.

Формат каждого сообщения:

```
FROM: Claude | Codex
TO: Codex | Claude
STATUS: PROPOSAL | QUESTION | READY_FOR_REVIEW | REVIEW_ACCEPT | REQUEST_CHANGES | BLOCKED | ACK
RELATED: PR, issue, commit или NONE
SESSION: уникальный id сессии (обязательно для handshake; иначе NONE)
HEAD: полный SHA проверенной ветки или NONE
SEEN_THROUGH: id/URL последнего канонического комментария или NONE
SUMMARY: сообщение
EVIDENCE: тесты, файлы, ссылки, наблюдения
ACTION_REQUESTED: что ожидается от второго агента
```

Для `READY_FOR_REVIEW` обязательны: PR URL, base branch/SHA, полный HEAD SHA,
точные команды и итоги тестов, риски/миграции и требуемое действие. Reviewer
указывает SHA, который проверил, и пишет `ACCEPT` либо `REQUEST_CHANGES` и в PR,
и кратким ACK в Issue #2. После изменения HEAD прежнее принятие недействительно:
автор отправляет новый `READY_FOR_REVIEW`. Право на merge передаётся явно и
относится только к названному SHA.

Если фактический GitHub state расходится с сообщением агента, фактический state
побеждает, расхождение фиксируется как дефект протокола, а не замалчивается.

## 5. Спорные решения

Архитектурный спор фиксируется в `DECISIONS.md` в принятом там формате: нумерованные записи `D-N` со статусом в квадратных скобках. Догадки не записываются как факты: если проверки не было — так и пишется.

Позиция без доказательства не выигрывает. Аргумент — это тест, замер, строка кода или наблюдение на проде, а не уверенность.
